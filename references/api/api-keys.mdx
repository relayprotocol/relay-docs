Relay enforces rate limits to keep the platform reliable for every integrator. You manage API keys in the [Relay Dashboard](https://dashboard.relay.link) — create new API keys, rotate existing ones, and inspect individual requests. Default limits listed below apply to self-serve API keys.

## Creating an API key

API keys are self-serve. To create one:

1. Sign in to the [Relay Dashboard](https://dashboard.relay.link).
2. Open the **API keys** tab.
3. Click **Create key**, give it a label (e.g. `production`, `staging`), and copy the key.

<Tip>
Use a separate key per environment (production, staging, local). Per-key request history makes it easy to spot a misbehaving deploy without revoking the wrong credential.
</Tip>

## Tracking requests

The [Relay Dashboard](https://dashboard.relay.link) is also where you observe what your integration is doing in production:

- **Requests** — full history of quotes and intents made with each key, with status, route, amounts, and timing.
- **Advanced filtering** — narrow the table by chain, currency, amount, status, time, and more, combining conditions with AND/OR logic to isolate exactly the requests you care about.
- **Custom views** — save any combination of filters, sort order, and columns as a reusable view for your team, each with its own name, icon, and color.
- **Keys** — create, rename, and revoke keys for your account.
- **Webhooks** — configure a per-key [webhook endpoint](/references/api/api_guides/webhooks) so transaction status updates are pushed to your backend instead of polling.

When debugging a specific transaction, paste the `requestId` from your application into the dashboard's search to jump straight to the matching record.

## Default Rate Limits

The following limits apply per API key:

| Endpoint               | Limit                   |
| ---------------------- | ----------------------- |
| `/quote`               | 50 requests per minute  |
| `/requests`            | 100 requests per minute |
| `/requests/v3`         | 200 requests per minute |
| `/transactions/status` | 200 requests per minute |
| Other endpoints        | 200 requests per minute |

## Elevated Rate Limits

Higher limits are available on request, applied per key:

| Endpoint               | Limit                                                                                                       |
| ---------------------- | ----------------------------------------------------------------------------------------------------------- |
| `/quote`               | 50 requests per second                                                                                      |
| `/requests/v3`         | 20 requests per second                                                                                      |
| `/requests`            | 5 requests per second                                                                                       |
| `/transactions/status` | 10 requests per second                                                                                      |
| `/authorize`           | 5 requests per minute per `(API key, wallet)`, with a 30 requests per minute aggregate ceiling per API key  |
| Other endpoints        | 200 requests per minute                                                                                     |

`/requests` and `/requests/v2` share the 5 rps bucket; `/requests/v3` has its own 20 rps bucket.

`/authorize` is bucketed by the `wallet` field in the request body alongside your API key, so concurrent authorizations from different end-users don't compete for the same bucket. The aggregate per-key ceiling still applies across all wallets and bounds total volume of the on-chain authorization path.

To request higher limits, get in touch through the support widget in the [Relay Dashboard](https://dashboard.relay.link).

<Tip>
Already hitting a limit? See [Handling Rate Limits](/references/api/api_core_concepts/handling-rate-limits) for how to recover from `429` responses and reduce your request volume before requesting an upgrade.
</Tip>

## How to Use an API key

<Warning>
Quote requests that set a `referrer` must be authenticated: pass your API key in the `x-api-key` header on `POST /quote` and `POST /quote/v2`. Requests with a referrer but no valid key return `401` with `errorCode: "UNAUTHORIZED_QUOTE"`. Starting **October 2, 2026**, every `quote/v2` request will require a valid API key. `quote/v2` remains fully supported for authenticated requests.
</Warning>

### HTTP requests

Pass the key in the request headers on every request:

```
x-api-key: YOUR_API_KEY
```

### SDK usage

<CodeGroup>

```typescript Global API key
// Set apiKey only when using the SDK server-side.
import {
  createClient,
  MAINNET_RELAY_API,
} from "@relayprotocol/relay-sdk";

createClient({
  baseApiUrl: MAINNET_RELAY_API,
  apiKey: "YOUR_API_KEY",
  // ...other parameters
});
```

```typescript SDK action API key
// Or pass the key per-call via the headers parameter.
import { getClient } from "@relayprotocol/relay-sdk";

const quoteParams = { /* ... */ };

const quote = await getClient()?.actions.getQuote(quoteParams, undefined, {
  "x-api-key": "YOUR_API_KEY",
});
```

</CodeGroup>

### Proxy API

If you're calling the SDK from the browser, stand up a proxy that appends the key server-side and point `baseApiUrl` at it. This keeps the key out of client bundles while preserving your key's rate limits.

```typescript
import {
  createClient,
  MAINNET_RELAY_API,
} from "@relayprotocol/relay-sdk";

createClient({
  baseApiUrl: "https://my-proxy.relay.link", // Replace with your proxy endpoint
  // ...other parameters
});
```

## Keeping Your API key Secure

Treat your API key like a password. It's tied to your account, controls your rate limits, and every request made with it is attributed to you.

<Warning>
If your key is leaked, anyone holding it can consume your rate limits or make requests on your behalf. Revoke and re-create the key in the [Relay Dashboard](https://dashboard.relay.link) immediately if you suspect it has been compromised.
</Warning>

**Best practices:**

- **Keep it server-side only** — never expose it in client-side or frontend code. Use a [proxy API](#proxy-api) if calling Relay from the browser.
- **Use environment variables** — store the key in environment variables, not hardcoded in source code.
- **Don't commit it to version control** — add it to `.gitignore` or use a secrets manager.
- **Restrict access** — only share the key with team members who need it.
- **Rotate regularly** — create a new key in the [Relay Dashboard](https://dashboard.relay.link) and revoke the old one whenever a team member with access leaves.

## Browser access tokens

A browser cannot safely carry a long-lived API key. Relay offers two patterns for integrations that call the API directly from a client:

- **Proxy API** (above) — your backend forwards every request and appends `x-api-key`. The browser never sees the key.
- **Access tokens** — your backend mints a short-lived JWT by calling [`POST /access-tokens`](/references/api/create-access-token). The browser then calls allowlisted public endpoints with that token in an `Authorization: Bearer <token>` header.

Access tokens are available on **tier 2 and higher** API keys. Each token lasts **15 minutes** and carries scope `public-api`.

### Minting a token

Your backend sends its API key in `x-api-key` on `POST /access-tokens` with an empty JSON body. The response is `Cache-Control: no-store` and contains:

| Property        | Description                                                                 |
| --------------- | --------------------------------------------------------------------------- |
| **token**       | The signed bearer credential. Pass this to the browser.                     |
| **tokenType**   | Always `"Bearer"`.                                                          |
| **expiresAt**   | ISO 8601 timestamp when the token expires. Renew by minting again.          |
| **scope**       | Always `"public-api"`.                                                      |

```bash
curl -X POST https://api.relay.link/access-tokens \
  -H "x-api-key: YOUR_API_KEY" \
  -H "content-type: application/json" \
  -d '{}'
```

<Warning>
Mint tokens from your backend only — never ship the long-lived API key to the browser. Protect the backend endpoint that forwards mint calls against automated abuse (rate-limit it, require your own session).
</Warning>

### Using a token from the browser

Pass the JWT in the `Authorization` header on every request, over HTTPS:

```
Authorization: Bearer <token>
```

Tokens work from any origin or IP and are not restricted by the parent key's IP/origin allowlist. Responses to session-authenticated requests are returned with `Cache-Control: private, no-store`.

### Endpoints that accept access tokens

Access tokens are accepted on these public endpoints:

- `POST /quote`, `POST /quote/v2`, `POST /price`
- `GET /intents/status`, `GET /intents/status/v2`, [`GET /intents/status/v3`](/references/api/get-intents-status-v3)
- `GET /requests/v2`, [`GET /requests/v3`](/references/api/get-requests)
- `POST /authorize`, `POST /execute`, `POST /execute/permits`
- `POST /transactions/index`, `POST /transactions/single`
- `GET /chains`, `GET /config`, `GET /config/v2`
- `GET /currencies/v2`, `GET /currencies/token-price`, `GET /currencies/token-price/v2`

All other endpoints — admin, dashboard, usage metrics, deposit-address management, request-metadata updates, screening management — require your original API key. Access tokens cannot mint further tokens.

### Request parameter restrictions

Session-authenticated requests only accept parameters that are explicitly allowed for session use. Unknown or unlisted parameters are rejected with `400` and `errorCode: "INVALID_REQUEST_PARAMS"`.

Fee-sponsorship and fixed-rate parameters (such as `subsidizeFees`, `subsidizeGas`, `useGasSubsidy`, `subsidizationBps`, and the fixed-rate fields) are not available with an access token. Keep those requests on your backend using the original API key.

### Browser rate limits

Browser requests share a per-minute allowance keyed by `(parent API key, client IP)`, separate from the parent key's backend quota:

| Endpoint family                               | Limit                      |
| --------------------------------------------- | -------------------------- |
| `POST /quote`, `POST /quote/v2`, `POST /price` | 60 requests per minute     |
| `GET /intents/status*`, `GET /requests*`      | 240 requests per minute    |
| Other allowlisted public endpoints            | 120 requests per minute    |
| `POST /access-tokens` (minting)               | 600 requests per API key per minute |

Different IPs under the same parent key have independent counters. Over-limit requests return `429` with `errorCode: "RATE_LIMITED"`.

### Errors

| Status | `errorCode`                | When                                                                                   |
| ------ | -------------------------- | -------------------------------------------------------------------------------------- |
| `401`  | `INVALID_API_SESSION`      | Token is missing, malformed, expired, has an invalid signature, or the parent key is revoked. Also returned when both `Authorization: Bearer` and `x-api-key` (or `x-dev-portal-key`) are supplied on the same request. |
| `403`  | `FORBIDDEN`                | Minting from a key below tier 2.                                                       |
| `400`  | `INVALID_REQUEST_PARAMS`   | Session request includes a parameter that is not allowed for session use.              |
| `429`  | `RATE_LIMITED`             | Browser or mint rate limit exceeded.                                                   |
| `500`  | `API_SESSION_UNAVAILABLE`  | Session infrastructure is temporarily unavailable.                                     |

### Revocation and rotation

Access tokens are not individually revocable. The following events invalidate existing tokens as cached authorization refreshes:

- The parent API key is disabled or deleted — all its outstanding tokens stop working.
- The parent key is dropped below tier 2.

Rotating the parent key's secret or editing its metadata does **not** revoke outstanding tokens — rely on the 15-minute expiry for those cases.

<Tip>
Access tokens are a thin shortcut for client-side calls. If you need granular per-user quotas, auditability tied to end-user identity, or sponsorship / fixed-rate parameters in the browser flow, keep using a server-side [Proxy API](#proxy-api).
</Tip>
