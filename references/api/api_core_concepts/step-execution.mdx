## Step Execution using the API

The [Relay platform](/references/api/overview) returns the steps needed to execute a quote, such as submitting a deposit transaction or signing a message. Follow the transaction targets, calldata, and amounts returned by the [quote endpoint](/references/api/get-quote-v3); they depend on the route and deposit method.

Step descriptions are display text, not a specification of fund ownership or settlement. Some API responses retain legacy “relayer” wording; use **`id`**, **`kind`**, and **`data`** to drive execution, and see [Input Validation](/references/api/api_core_concepts/input-validation) for verifying protocol deposits.

The flow looks like this:

<Steps>
  <Step title="Fetching Steps" icon="server">
    Call the [Get Quote API](/references/api/get-quote-v3) to start your
    execution.
  </Step>
  <Step title="Iterate Through Steps" icon="list-ul">
    Iterate through the steps in array order, taking the necessary actions.
    Skip steps whose `status` is already `complete`. Step ids can repeat, so
    track each step by its position rather than its id.
  </Step>
  <Step title="Executing Steps" icon="list-check">
    Each step carries its own `status`, `data`, and `check`. Complete it
    according to its kind ([signature](#signature-step) or
    [transaction](#transaction-step)).
  </Step>
  <Step title="Checking the fill status" icon="bars-progress">
    After a step is signed or submitted you should check on the progress of the
    fill
  </Step>
  <Step title="Success!" icon="circle-check">
    Once all the steps are complete you can consider the action complete and
    notify the user.
  </Step>
</Steps>

### Signature Step

A message that needs to be signed. Every signature comes with sign data and post data. The first action we need to take is to sign the message, keep in mind the signatureKind and use the appropriate signing method. Refer to your crypto library of choice on how to sign (viem, web3, etc).

<CodeGroup>

```javascript Signing EIP191
// Creating an `EIP-191` signature involves signing a message.
// When you receive a `signatureKind: "eip191"` from the API, you will sign the value associated with the `message` property.
// In the case below, the message `Sign in to Blur...` will be signed, and later posted to the API.
// The step data also contains a `post` object detailing the endpoint to post the signed message to.
const message = {
  signatureKind: "eip191",
  message:
    "Sign in to Blur\n\nChallenge: e2483db1d9d66d2b77f47a8dfa13a15a0e7df5aee2287ade4bf313d6d4bdd0e0",
};

const eip191Message =
  "\x19Ethereum Signed Message:\n" + message.message.length + message.message;
```

**Posting the data**

After the message is signed the second action is to submit the `post` body to the `endpoint` provided in the `post` data. You'll also need to provide the signature that was generated from the sign data as a query parameter. If the request is successful we can mark the step as complete locally. Always post to the step's own `data.post.endpoint`: permit signatures from `/quote/v3` point to [`/execute/permits/v2`](/references/api/execute-permits-v2), while other signatures, such as Hyperliquid nonce mappings, use their own endpoint. When a `/execute/permits/v2` response includes `steps`, run those transaction steps before the remaining quote steps.

The design pattern of this API is completely generic, allowing for automatic support of new types of liquidity without needing to update the app. This data can be fed directly into an Ethereum library such as viem, making it easy to sign and submit the exact data that is needed.

**Consecutive signature steps**

A quote can return more than one signature step in a row, with the same id. Sign and post them in the order they appear: a later signature can be refused until the earlier one is posted. Not every step has a `check`; for example, the `MulticallAuthorization` step of an [ERC-3009 permit](/features/gasless-swaps#erc-3009-permits-with-multicallauthorization) has none.

### Transaction Step

A transaction that needs to be submitted onchain. After the transaction is submitted onchain you can poll the step's `check` endpoint. The endpoint will return a status which when successful will return 'success'. The step can then be successfully marked as complete. Submit the transaction on the chain given by the step's **`data.chainId`**.

## Step IDs

Each step has an `id` that identifies the type of action required. Ids can repeat within one quote, for example two `approve` steps when a token needs its allowance reset first. Understanding these step IDs helps you build better UX and handle each step appropriately.

### Transaction Steps

| Step ID                   | Description                                            | When Used                                                                           |
| ------------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| [`deposit`](#deposit)     | Submit the quoted deposit for cross-chain execution   | Used for cross-chain swaps and bridges.                                             |
| [`approve`](#approve)     | Approve the transfer of an ERC20 token                 | Used before `deposit` or `swap` when the quoted flow requires a token allowance. |
| `swap`                    | Execute a same-chain token swap                        | For same-chain swaps. May require an approval step first for EVM swaps.             |
| [`send`](#send)           | Send funds to the recipient                            | When sending the same asset on the same chain to a different recipient.             |

### Signature Steps

| Step ID                       | Description                                | When Used                                                                                                                                                                                                      |
| ----------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`authorize`](#authorize)     | Sign an authorization or permit            | Used for: (1) [cross-chain permits](#cross-chain-permit) with Permit2 or EIP-3009, (2) [same-chain ERC-20 → native permits](#same-chain-permit) with Permit2, (3) [Hyperliquid](/references/api/api_guides/hyperliquid-support) v2 deposits, a nonce-mapping signature, (4) claiming [app fees](/features/app-fees), an EIP-191 signature to verify wallet ownership. Same-chain ERC-20 → ERC-20 swaps return `approve` → `swap` transactions instead; see [Gasless Swaps](/features/gasless-swaps#permit-based-gasless). |

### Common Step Flows

Depending on the action and tokens involved, Relay chains steps together. Here are common flows you may encounter:

| Flow                                                | Description                                     |
| --------------------------------------------------- | ----------------------------------------------- |
| [`deposit`](#deposit)                               | Single step for cross-chain swaps/bridges       |
| `swap`                                              | Single step for same-chain swaps                |
| [`approve`](#approve) → [`deposit`](#deposit)       | Approval needed before deposit for ERC20 tokens |
| [`approve`](#approve) → `swap`                      | Same-chain swap requiring approval              |
| [`authorize`](#cross-chain-permit)                  | Cross-chain permit-based transfer (gasless)     |

### authorize

Sign authorization for specific operations. This step is used in two scenarios:

1. **Permits**: Signs a Permit2 or EIP-3009 authorization for a gasless deposit or same-chain swap. See the examples below.
2. **Hyperliquid Deposits**: Signs a nonce-mapping signature for v2 Hyperliquid deposits.
3. **Claiming App Fees**: Signs an EIP-191 message to verify wallet ownership before claiming accrued app fees.

The [app fee claim API](/references/api/claim-app-fees) still returns its signature in a step's `items` array and posts it to `/execute/permits`:

```json expandable App Fee Claim Example
{
  "id": "authorize",
  "action": "Sign authorization",
  "description": "Authorize claiming funds",
  "kind": "signature",
  "items": [
    {
      "status": "incomplete",
      "data": {
        "sign": {
          "signatureKind": "eip191",
          "message": "0xa344c6123e3da9fc3f9c81edeab0b2eb39f2ea80ba54a6e0ad00123dc180619c"
        },
        "post": {
          "endpoint": "/execute/permits",
          "method": "POST",

            "kind": "claim",
            "requestId": "0xa344c6123e3da9fc3f9c81edeab0b2eb39f2ea80ba54a6e0ad00123dc180619c"
```

### Checking the fill status

Along with the step data there's an optional check object. You can use this object to check if the status of the transaction is complete. The object details the method and the endpoint to request. You should poll this until the endpoint returns `success`.

```json
{
  "check": {
    "endpoint": "/intents/status/v3?requestId=0x341b28c6467bfbffb72ad78ec5ddf1f77b8f9c79be134223e3248a7d4fcd43b6",
    "method": "GET"
  }
}
```

The check api will always return a status, to get a full list of statuses, please refer to the [Get Status](/references/api/get-intents-status-v3) API Reference.
