## Overview

The limit orders API has four endpoints:

| Method | Path | Purpose | SDK action | API key needs |
| --- | --- | --- | --- | --- |
| `POST` | `/orders` | [Create an order](/limit-orders/create-order) | `createOrder` | Limit orders enabled for its app |
| `POST` | `/orders/{orderId}/signature` | [Sign an order](/limit-orders/sign-order), which opens it | `signOrder` | Limit orders enabled for its app |
| `GET` | `/orders` | [List orders](/limit-orders/list-orders), or read one by id | `getOrders` | Any active key of the app |
| `POST` | `/orders/{orderId}/cancel` | [Cancel an order](/limit-orders/cancel-order) | `cancelOrder` | Any active key of the app |

Relay sends status changes to your server with the [order.updated webhook](/limit-orders/webhook).

**Relay SDK.** The actions above are on `getClient().actions` in `@relayprotocol/relay-sdk`, along with `executeOrder`, which runs an order's `steps` with a wallet. Given a `wallet`, `createOrder` and `cancelOrder` also run the steps they return. The SDK returns the order itself rather than `{ order }`, and throws an `APIError` on failure, with the API's `errorCode` in `error.rawError.errorCode`. Pass `apiKey` to `createClient` only on your server; in the browser, point `baseApiUrl` at a proxy that adds the key.

**Ownership.** Orders belong to the app whose key created them, not to the key itself. Any active key of that app can read and cancel the app's orders, and open orders keep running when you rotate the key that created them. Another app's order returns `404 ORDER_NOT_FOUND`.

## Order values

Each endpoint page lists every field of the Order object from the API spec. The tables below explain the values that the spec only lists by name.

### Steps

Each step carries its own `status`, `data`, and `check`. Send a `transaction` step's `data` as a transaction; sign a `signature` step's `data.sign`, then post to `data.post`.

| Step | When it appears |
| --- | --- |
| `approve` | On a `pending` order, when the wallet hasn't approved Permit2 for the token. A transaction that approves Permit2. |
| `authorize` | On a `pending` order. The Permit2 permit to sign; its `post` is `/orders/{orderId}/signature` and its `check` is `GET /orders?orderId={orderId}`. |
| `cancel` | After an onchain cancel, while the permit is still valid and unused. A transaction to Permit2 that burns the permit's nonce. |
| `withdraw` | Reserved. No order produces it during the beta. |

### Statuses

| `status` | Meaning |
| --- | --- |
| `pending` | Created and waiting for the user's signature. |
| `open` | Signed. Relay is watching the price and the funds are still in the user's wallet. This includes the moment Relay pulls the funds, and an order whose pull failed, which goes back to waiting. |
| `processing` | Relay holds the funds: a fill or a refund is under way, or Relay is retrying after a failed fill. |
| `requires_action` | The order needs an action before it can continue. `requiredAction` says which. |
| `closed` | Final. See `outcome`. |

Statuses only move forward. An order past `expiresAt` that Relay never took funds for reads as `closed` with `outcome: "expired"`.

### Outcomes

| `outcome` | Meaning |
| --- | --- |
| `filled` | The order filled. See `filledAmount`. |
| `cancelled` | Cancelled; see `cancellationReason`. If Relay held the funds, they were refunded first; see `refundedAmount`. |
| `expired` | `expiresAt` passed before the order filled or was signed. If Relay held the funds, they were refunded first; see `refundedAmount`. |

An order whose funds can be neither delivered nor returned doesn't close: it stays `requires_action`.

### Required actions

| `requiredAction` | Meaning |
| --- | --- |
| `compliance_review` | A wallet check stopped the fill, and Relay is reviewing it. |
| `manual_refund` | Relay couldn't send the refund automatically and will refund the funds manually. |

More values may be added, so handle an unknown `requiredAction` by showing the order as needing attention.

### Price check reasons

`reason` on `latestPriceCheck` and `closestPriceCheck` says why a check didn't start a fill. Relay checks in this order and reports the first that applies; prices are still filled in when the order could be quoted.

| `reason` | Meaning |
| --- | --- |
| `insufficient_balance` | The wallet holds less than `amount` of the currency it spends. |
| `insufficient_allowance` | The wallet's Permit2 allowance for the token is below `amount`. |
| `no_route` | No route can currently quote the order. |
| `price_not_reached` | The all-in price hasn't reached `targetPrice`. |

`reason` is `null` when nothing stopped the fill. An order short of balance or Permit2 allowance doesn't trigger; it stays `open` until the user fixes it or the order expires.

### Cancel reasons

| `cancellationReason` | Meaning |
| --- | --- |
| `requested` | You cancelled the order. |
| `access_revoked` | Relay cancelled it because your app lost access to limit orders. |

## Errors

Errors return `{ message, errorCode, errorData?, requestId? }`. `errorData` holds the error's details when it has any, such as the quote's details behind a `NO_QUOTES`.

`requestId` names the Relay request a failed create ran under, once create has started quoting the order; include it when you contact support. Schema validation errors, such as a missing field or a bad format, return only `message`, for example `{"message":"body must have required property 'type'"}`.

| `errorCode` | Status | Endpoints | When |
| --- | --- | --- | --- |
| `INVALID_REQUEST_PARAMS` | 400 | Create, sign | `expiresAt` outside 15 minutes to 7 days; target and settlement are the same currency; sponsorship options without `subsidizeFees`; `targetPrice` and `amount` give a zero minimum output; a sign request without a signature. |
| `INVALID_ADDRESS` | 400 | Create | `user` isn't a valid EVM address. |
| `UNSUPPORTED_CURRENCY` | 400 | Create | The target is the native currency; a buy's target isn't held by Relay; a sell's target isn't a token on its chain; the settlement currency isn't an accepted stablecoin. |
| `UNSUPPORTED_ROUTE` | 400 | Create | The currency spent isn't on an EVM chain, or the origin chain doesn't support swapping a token Relay doesn't hold. |
| `AMOUNT_TOO_LOW` | 400 | Create | The amount is too small to cover fees and the route's minimums. There is no fixed minimum order size. |
| `NO_QUOTES` | 400 | Create | Any other reason the order can't be quoted, such as no route, an amount that is too high, or an invalid app fee recipient. `message` says which. |
| `INSUFFICIENT_FUNDS` | 400 | Create | The wallet holds less than `amount` of the currency it spends. |
| `MAX_OPEN_ORDERS_REACHED` | 400 | Create, sign | The wallet already has 100 `open` or `processing` orders. |
| `MAX_OPEN_ORDER_PAIRS_REACHED` | 400 | Create, sign | The wallet's `open` and `processing` orders are already on 50 token pairs, and this order is on another pair. |
| `INVALID_SIGNATURE` | 400 | Sign | The signature isn't the `user`'s signature of the order. |
| `UNAUTHORIZED` | 401 | All | Missing or invalid API key. |
| `FORBIDDEN` | 403 | Create, sign | The key's app doesn't have limit orders enabled. |
| `ORDER_NOT_FOUND` | 404 | Sign, cancel | No order with this id in your app. |
| `IDEMPOTENCY_KEY_REUSED` | 409 | Create | The `Idempotency-Key` already created an order from a different body. |
| `CLIENT_ORDER_ID_EXISTS` | 409 | Create | The `clientOrderId` already belongs to an order created with another `Idempotency-Key` or none. |
| `ORDER_ALREADY_SIGNED` | 409 | Sign | The order is already signed. Treat it as success. |
| `ORDER_NOT_PENDING` | 409 | Sign | The order closed without being signed: it was cancelled while `pending` or expired. |
| `ORDER_ALREADY_CANCELLED` | 409 | Cancel | The order is already cancelled, or its cancel is waiting on a refund. |
| `ORDER_NOT_CANCELLABLE` | 409 | Cancel | The order can't be cancelled in its current state. |
| `UNKNOWN_ERROR` | 500 | All | An unexpected error: "Could not process request", with `requestId` when the call had one. Safe to retry; on create, retry with the same `Idempotency-Key`. |

## Limits

| Limit | Value |
| --- | --- |
| Order lifetime (`expiresAt`) | At least 15 minutes and at most 7 days from create |
| `open` and `processing` orders per wallet | 100, across all integrators and chains |
| Token pairs with `open` or `processing` orders per wallet | 50 |
| `Idempotency-Key` | 1–255 characters, per app, never expires |
| `clientOrderId` | 1–128 characters, once per app |
