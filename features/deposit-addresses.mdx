Deposit addresses let users bridge or swap tokens by sending funds to an address, without connecting a wallet to your application. You request a quote with **`useDepositAddress: true`**, and the user transfers funds to the returned address. Relay detects the deposit and tracks execution, and a solver fills the order on the destination chain.

This makes deposit addresses a good fit for CEX withdrawals, fiat onramps, and headless systems where the sender can't sign transactions. The user just sends to an address, with the same UX as a normal transfer.

## How It Works

1. **Quote** — Request a quote with `useDepositAddress: true`. The response includes a `depositAddress` and a `requestId`.
2. **Deposit** — The user sends funds to the deposit address, from a wallet or an exchange withdrawal.
3. **Detect and sweep** — Relay detects the deposit and moves the funds into the [Relay Depository](/references/protocol/components/depository). An `EXACT_INPUT` address prices the order for what actually arrived. An `EXACT_OUTPUT` address checks the deposit against the quote.
4. **Fill** — For cross-chain orders, a solver uses its own liquidity to deliver the output to the recipient. Same-chain swaps execute on the deposit chain.

See [Deposit Addresses](/references/protocol/components/deposit-addresses) in the Relay Protocol docs for how Relay sweeps deposits into the Depository.

### Key Parameters

The deposit-address parameters for `POST /quote/v2` are below; see [Get Quote](/references/api/get-quote-v2) for the full list.

| Parameter | Type | Details |
|---|---|---|
| `useDepositAddress` | boolean | Set to `true` to receive a deposit address instead of transaction calldata. |
| `user` | address | The user address for the quote. Can be any valid address, including the zero address. |
| `recipient` | address | The address that receives funds on the destination chain. |
| `refundTo` | address | **Required.** The origin-chain address that receives refunds. Set it to the origin chain's native-currency address (EVM `0x0000000000000000000000000000000000000000`, Bitcoin `bc1qqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqmql8k8`, Solana `11111111111111111111111111111111`) to refund the original sender instead. See [Refund Behavior](#refund-behavior). |
| `recoveryAddress` | address | Optional. An origin-chain wallet you control that can withdraw funds Relay can't refund automatically. See [`recoveryAddress`](#recoveryaddress). |
| `tradeType` | string | `EXACT_INPUT` fills whatever amount arrives at the current rate. `EXACT_OUTPUT` delivers a fixed output and expects the quoted input amount. `EXPECTED_OUTPUT` is not supported. |
| `amount` | string | The quoted amount in the origin token's smallest unit. For `EXACT_INPUT`, the user can send a different amount. |
| `strict` | boolean | Set to `true` for a single-use address. Omit or set to `false` for a reusable address. |

### Address Reuse

An **open** address accepts any number of deposits. Each deposit fills to the same destination chain, currency, and recipient, with the fee settings from the original quote.

A **strict** address accepts one deposit. Relay refunds any later deposit to `refundTo`. Use strict addresses for single-use payment instructions, such as one address per invoice.

## Open vs Strict Deposit Addresses

Two settings control how a deposit address behaves. `strict` decides whether the address is reusable. `tradeType` decides how Relay handles a deposit that doesn't match the quote.

### Open Deposit Addresses

Open deposit addresses are the default. They're reusable and tolerate user variability, so they suit general-purpose integrations and per-user addresses.

- Use `tradeType: "EXACT_INPUT"`.
- The user can send any amount, and any [supported token](#supported-currencies) on the address's chain.

### Strict Deposit Addresses

Strict deposit addresses accept one deposit and then stop filling. They suit payment flows that need one predictable outcome per address, such as checkouts and invoices.

- Set `strict: true` in your `/quote/v2` request.
- With `tradeType: "EXACT_INPUT"`, the first deposit fills at the current rate, whatever its amount.
- With `tradeType: "EXACT_OUTPUT"`, the recipient gets exactly the quoted output. The deposit must be the quoted token and at least the quoted amount. `EXACT_OUTPUT` addresses are always single-use.

### Comparison

How Relay handles each kind of deposit:

| Deposit | `EXACT_INPUT` | `EXACT_OUTPUT` |
|---|---|---|
| Quoted token and amount | Fills | Fills |
| More than quoted | Fills the full amount at the current rate | Fills the quoted output and refunds the surplus |
| Less than quoted | Fills the smaller amount at the current rate. Refunds it if it's too small to cover fees | Refunds the full deposit. The address still accepts a correct deposit |
| Different supported token | Requotes in the token received and fills | Refunds the full deposit |
| Unsupported token | Not processed. See [Supported Currencies](#supported-currencies) | Not processed |
| Same address, different EVM chain | Fills from the chain the funds landed on, if that chain and token are supported | Not processed automatically. Contact [Support](/resources/support) |
| Later deposit to the same address | Open: fills as a new order. Strict: refunded | Refunded |

A deposit can't land on a different VM by mistake. Address formats differ across VMs (EVM, Solana, Bitcoin, and others), so an EVM address can't receive funds on Solana.

## Refund Behavior

Relay refunds a deposit to `refundTo` when it can't fill it. Refunds are paid on the origin chain in the deposited token, minus the gas cost of the refund.

### Refund Flows

Relay refunds automatically in these cases:

- **The fill fails**, for example because of slippage.
- **The deposit is too small** to cover fees.
- **An `EXACT_OUTPUT` deposit doesn't match the quote.** An underpayment or a different supported token is refunded in full, and an overpayment's surplus is refunded.
- **A strict address receives another deposit.** Every deposit after the first is refunded.

Relay can't refund a deposit that is too small to cover the refund's gas. It also doesn't return [unsupported tokens](#supported-currencies), or deposits to an `EXACT_OUTPUT` address on the wrong chain. Contact [Support](/resources/support) with the deposit transaction for these.

If Relay can't send a refund, for example because the refund address is blocked, the funds stay in the Relay Depository. The depositor recorded for the order can [withdraw](/references/protocol/guides/withdrawals) them. That depositor is the `refundTo` or `recoveryAddress` you set on the quote.

### `refundTo` Configuration

`refundTo` is required on every deposit-address quote. A request without it fails with `400`.

| `refundTo` value | Behavior |
|---|---|
| User's address | Refund directly to the user. |
| App-controlled address | Refund to your address. Your support team returns funds to the user. |
| Origin chain's native-currency address (EVM `0x0000000000000000000000000000000000000000`, Bitcoin `bc1qqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqmql8k8`, Solana `11111111111111111111111111111111`) | Refund to the original sender, the address that sent funds to the deposit address. Supported on EVM, Bitcoin, Solana, and TON origins, and rejected on other chains, including Tron. If the sender is a known exchange address or is blocked, Relay doesn't refund it. Your [`recoveryAddress`](#recoveryaddress) can withdraw the funds instead. Without one, contact [Support](/resources/support). |

<Note>
If users may send from a centralized exchange, **do not set `refundTo` to the user's address**, explicitly or through the native-currency option. The sender is the exchange's hot wallet, not the user. Use an app-controlled address so your support team can handle the last mile, or pair the native-currency option with a [`recoveryAddress`](#recoveryaddress).
</Note>

<Info>
When a refund goes to the original sender, the request's `outTxs` contains **two** refund transactions. The first returns funds to the sender, so track that one. The second is an internal protocol-settlement transaction that doesn't move user funds.
</Info>

<Warning>
Set `refundTo` and `recoveryAddress` to wallets that can sign a Relay withdrawal on the origin chain. Either address can become the protocol depositor, and withdrawing is then the only way to recover the funds, so an address that can only receive funds, such as an exchange deposit address, is not enough. See [Supported Chains and Signers](/references/protocol/guides/withdrawals#supported-chains-and-signers) for which wallets can withdraw.
</Warning>

### `recoveryAddress`

`recoveryAddress` is a fallback for funds Relay can't refund automatically. It's most useful when `refundTo` is the native-currency address, because the sender may turn out to be an exchange or a blocked wallet.

Relay doesn't send refunds to `recoveryAddress`. Instead, it can [withdraw](/references/protocol/guides/withdrawals) the funds from the Relay Depository and send them on.

Constraints:

- Requires `useDepositAddress: true`. The request is rejected otherwise.
- Must be a valid address on the origin chain, and can't be the origin chain's native-currency address.
- Doesn't replace `refundTo`, which is still required.

### Recommended Setup

- **Users deposit from a wallet they control** — Set `refundTo` to the native-currency address to refund the sender, and add a `recoveryAddress` as a fallback.
- **Users may deposit from an exchange** — Set `refundTo` to an app-controlled wallet, and handle returns to the user yourself.
- **Either way** — Use wallets that can sign a withdrawal on the origin chain.

## Tracking Transactions

The `requestId` in the quote response is not always the request that fills. Depending on what arrives at the address, the sweep and fill can move to a new `requestId` (see [Which Request Owns the Fill](#which-request-owns-the-fill)). Treat the deposit address as the stable identifier for the order.

### Which Request Owns the Fill

The quote-time `requestId` tracks the first deposit to the address, including when Relay requotes it or refunds it in full. Every later deposit to an open address gets its own `requestId`.

Poll by `depositAddress` rather than by the quote-time `requestId`, so you see every request in one query. An open address can return several requests, one per deposit. When `depositAddress.depositTxHash` is populated, use it to match each request to the transfer that funded it.

### Handling Quote Regeneration

When a deposit moves to a new `requestId`, the quote-time `requestId` may not reach `success`. `GET /intents/status/v3` can keep returning `waiting` for it, even after the new request succeeds.

<Warning>
A quote-time `requestId` that stays `waiting` doesn't mean the deposit is stuck. Check the deposit address with `GET /requests/v3` before treating it as missing.
</Warning>

### Request-Level Status

Once the `depositAddress` query returns the request that owns the fill, you can poll its `requestId` with [Get Status](/references/api/get-intents-status-v3). To avoid polling, configure a [webhook](/references/api/api_guides/webhooks) instead. Webhook events are sent under the request that owns the fill, so a regenerated request's events carry the new `requestId` — match them to your order with `depositAddress.address` in the payload.

<CodeGroup>
```bash Request
curl -X GET "https://api.relay.link/intents/status/v3?requestId=<REQUEST_ID>"
```

### Reindexing Stuck Deposits

Relay detects deposits automatically, including supported tokens other than the one quoted. For EVM addresses, Relay also detects deposits on other supported EVM chains. If a deposit hasn't been picked up after a few minutes, call the [Deposit Address Reindex](/references/api/deposit-address-reindex) endpoint.

Pass the deposit's `txHash` whenever you have it, so Relay can find the deposit directly.

```bash
curl -X POST 'https://api.relay.link/transactions/deposit-address/reindex' \
  -H 'Content-Type: application/json' \
  -H 'x-api-key: YOUR_API_KEY' \
  -d '{
    "chainId": 8453,
    "depositAddress": "0x1ba74e01d46372008260ec971f77eb6032b938a4",
    "txHash": "0xf93e6174d36c103f31cdbb1e4006df949b9c0d86fa9ec74aaa6958898d91993f"
  }'
```

`chainId` is the chain the deposit address was created for. Reindexing is idempotent, and repeated calls for the same address are rate limited. A successful response only queues detection, so keep tracking the address until the request completes.

<Note>
The deposit transaction hash can't be used to look up an order's status. Track status by the deposit address, and use a `requestId` only once the `depositAddress` query has returned it.
</Note>

## Caveats

### Gas Overhead

Relay pays the gas to move each deposit into the Relay Depository and includes it in the quote's fees. On small deposits, that gas is a larger share of the amount, so direct calldata execution can be cheaper.

### Minimum Deposit

Deposit addresses have no fixed minimum. A deposit too small to cover fees isn't filled. Relay refunds it to `refundTo` when the amount covers the refund's gas, and otherwise leaves it unprocessed.

Quotes below a route's minimum return [`AMOUNT_TOO_LOW`](/references/api/api_core_concepts/handling-errors). Open addresses accept any amount, so enforce your own minimum in your app.

### Supported Currencies

Deposit addresses process only **solver currencies** that are enabled for deposit addresses on the chain. The destination token can differ and is completed through a destination-side swap. To list eligible input tokens, call [Get Currencies](/references/api/get-currencies-v2) with **`depositAddressOnly: true`**.

Relay treats certain tokens as equivalent within currency groups, such as ETH and WETH. Depositing any token in a group triggers the same fill behavior.

### Chain-Specific Notes

- **Bitcoin** — Relay detects deposits in the mempool and processes them after they confirm onchain.
- **Solana** — Supports native SOL and SPL tokens, such as USDC, that are solver currencies on Solana.
- **Tron** — Supports TRX and USDT. `refundTo` must be an explicit address, because Tron doesn't support refunds to the original sender.
- **Hyperliquid** — Uses bridged USDC (USDC.e) with different decimal precision than native USDC on other chains. Account for the decimal difference when computing amounts.

### Other Limitations

- Calldata execution on the destination chain (`txs`) is not supported.
- `EXPECTED_OUTPUT` is not supported. Use `EXACT_INPUT` or `EXACT_OUTPUT`.
