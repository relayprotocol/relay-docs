---
title: "Gasless Swaps"
description: "Remove gas friction from swaps so users only pay with the input token"
---

Gas fees add layers of complexity to swapping. Holding the native token, on the right network, at the right time to pay for gas adds friction for users. A gasless swap means that the user only pays with the input token, and this covers all fees. This means someone else is executing the transaction and paying the gas.

## What solution is right for me?

There are many different solutions when it comes to implementing a gasless swap experience. We've put together a decision tree below to help you arrive at the solution that best fits your application.

  Same-chain gasless swaps are only supported if you sponsor the fees. Same-chain swaps route directly through DEXes, due to this the solver never has an opportunity to deduct the gas fees before the user gets the destination token.

## Permit-based Gasless

Use this approach when your app does **not** control the user's wallet (e.g. MetaMask, Rainbow, or any external EOA). The user signs an offchain EIP-3009 or Permit2 message and submits it through the Relay platform. Solvers execute the authorized flow and pay transaction gas.

<Warning>
  USDC is fully gasless. Other ERC-20 tokens require a one-time approval transaction. Same-chain ERC-20 → ERC-20 swaps do not support the permit flow: passing **`usePermit: true`** is ignored and the quote returns `approve` and `swap` transaction steps instead of a permit signature step. Same-chain ERC-20 → native swaps do return the [`authorize2`](/references/api/api_core_concepts/step-execution#authorize2) permit step.
</Warning>

### How it works

<Steps>
  <Step title="Get a quote">
    Call `/quote/v2` with `usePermit: true`
  </Step>
  <Step title="Sign the permit">
    Prompt the user to sign an EIP-712 typed-data permit message (off-chain, no gas)
  </Step>
  <Step title="Submit to Relay">
    Submit the signed permit to Relay
  </Step>
  <Step title="Fulfillment">
    The signed permit authorizes the token transfer. A solver completes the destination transaction using its own capital.
  </Step>
</Steps>

### Fees

You can choose to subsidize all destination fees by passing `subsidizeFees: true` to the quote api (this effectively subsidizes the first time approval). The user still needs to pay for the origin gas fee. For subsidizing fees you'll need to make sure you have [fee sponsorship](/features/fee-sponsorship) set up.

_See the full working example: [<Icon icon="github" size={16} /> byo-eoa-permit](https://github.com/relayprotocol/relay-gasless-examples/tree/main/byo-eoa-permit)_

## ERC-4337 Gasless

Use this approach if your app already uses ERC-4337 smart accounts. ERC-4337 UserOperations normally require gas fees, either paid by the sender or a paymaster. Set all gas fee fields to 0 and submit the `handleOps` call through the platform's [/execute](/references/api/execute) endpoint; a relayer broadcasts the transaction and pays gas.

### `originGasOverhead`

Pass **`originGasOverhead: 300000`** in the `/quote/v2` request. This tells Relay how much additional gas the UserOperation adds over a normal EOA transaction, used during simulation to accurately price the fee.

### How it works

<Steps>
  <Step title="Get a quote">
    Call `/quote/v2` with `originGasOverhead: 300000` to get deposit transaction details
  </Step>
  <Step title="Build the UserOperation">
    Build a UserOperation that batches `approve` + `deposit` calls via `executeBatch`
  </Step>
  <Step title="Zero out gas fields">
    Set **`maxFeePerGas`** and **`maxPriorityFeePerGas`** to `0`
  </Step>
  <Step title="Sign the UserOperation">
    Sign the UserOperation with the account owner key
  </Step>
  <Step title="Submit via Relay">
    Encode an `EntryPoint.handleOps()` call and submit it via `POST /execute` with `subsidizeFees: true`
  </Step>
  <Step title="Monitor">
    Poll `/intents/status/v3` until the bridge completes
  </Step>
</Steps>

### Fees

You can choose to subsidize origin fees: pass `subsidizeFees: true` to the execute api `executionOptions`.

You can choose to subsidize destination fees: pass `subsidizeFees: true` to the quote api.

You can choose to subsidize both or none of these. If not subsidized the user pays from the output token.

For subsidizing fees you'll need to make sure you have [fee sponsorship](/features/fee-sponsorship) set up.

_See the full working example: [<Icon icon="github" size={16} /> 4337-gasless](https://github.com/relayprotocol/relay-gasless-examples/tree/main/4337-gasless)_

## 7702 BatchExecutor

Use this approach when your app controls an embedded or custodial wallet and you want gasless execution with **any** ERC-20 token — not just permit-compatible ones. This leverages EIP-7702 to delegate the user's EOA to a BatchExecutor contract ([Calibur](https://github.com/Uniswap/calibur) or similar), enabling atomic approve + deposit in a single call.

### `originGasOverhead`

Pass **`originGasOverhead: 80000`** in the `/quote/v2` request. This tells Relay how much additional gas the Calibur `execute()` wrapper adds over the raw inner calls (EIP-712 signature verification, batch dispatch, nonce check). This is lower than ERC-4337's `300000` because there's no EntryPoint or UserOp validation overhead.

<Info>
  The `80000` value is specific to [Calibur](https://github.com/Uniswap/calibur). Different BatchExecutor contracts may have different gas overheads — adjust this value based on the implementation you use.
</Info>

### How it works

<Steps>
  <Step title="Check delegation">
    Check if the user's EOA is already delegated to the BatchExecutor via EIP-7702
  </Step>
  <Step title="Get a quote">
    Call `/quote/v2` with `originGasOverhead: 80000` to get deposit transaction details
  </Step>
  <Step title="Build the batch">
    Build a `BatchedCall` that atomically combines `approve()` and `deposit()`
  </Step>
  <Step title="Sign the authorization">
    Sign an EIP-7702 authorization (off-chain, no gas) delegating the EOA to the BatchExecutor
  </Step>
  <Step title="Submit via Relay">
    Submit via POST [/execute](/references/api/execute) targeting the user's EOA
  </Step>
</Steps>

### Fees

You can choose to subsidize origin fees: pass `subsidizeFees: true` to the execute api `executionOptions`.

You can choose to subsidize destination fees: pass `subsidizeFees: true` to the quote api.

You can choose to subsidize both or none of these. If not subsidized the user pays from the output token. 

For subsidizing fees you'll need to make sure you have [fee sponsorship](/features/fee-sponsorship) set up.

_See the full working example: [<Icon icon="github" size={16} /> 7702-batch-executor](https://github.com/relayprotocol/relay-gasless-examples/tree/main/7702-batch-executor)_

## Gasless Swaps on Solana

Use this approach for Solana-origin trades, where permits do not exist. A sponsor wallet your app controls pays the transaction fees and rent, so your users need zero SOL: pass **`depositFeePayer`** in the quote, and your app co-signs each transaction as the fee payer.

You need a sponsor wallet funded with SOL (your backend holds its key; it never touches the client), a Relay [API key](/references/api/api-keys), and `@solana/web3.js` on your backend.

Three restrictions from [Solana Fee Sponsorship](/features/fee-sponsorship#solana-fee-sponsorship) apply to every step below:

1. **`depositFeePayer`** must be a different address from **`user`**. The quote API does not enforce this, so your app must.
2. The sponsor signs the transaction before the user. Signing in the other order lets the user modify the transaction and drain the sponsor.
3. Do not use **`depositFeePayer`** for same-chain Solana swaps with untrusted users. That combination is exploitable.

### How it works

<Steps>
  <Step title="Get a quote with a sponsor" id="get-a-quote-with-a-sponsor">
    Call `/quote/v2` with **`depositFeePayer`** set to your sponsor wallet.

    ```bash
    curl -X POST "https://api.relay.link/quote/v2" \
      -H "Content-Type: application/json" \
      -H "x-api-key: YOUR_API_KEY" \
      -d '{
        "user": "USER_SOLANA_ADDRESS",
        "recipient": "RECIPIENT_ADDRESS",
        "originChainId": 792703809,
        "originCurrency": "EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v",
        "destinationChainId": 8453,
        "destinationCurrency": "0x833589fcd6edb6e08f4c7c32d4f71b54bda02913",
        "tradeType": "EXACT_INPUT",
        "amount": "5000000",
        "depositFeePayer": "SPONSOR_SOLANA_ADDRESS"
      }'
    ```

    The response's `deposit` step carries raw `instructions`, `addressLookupTableAddresses`, and a `check` endpoint for tracking.
  </Step>
  <Step title="Assemble the transaction" id="assemble-the-transaction">
    On your backend, build a versioned transaction from the returned instructions with the sponsor as **`payerKey`** (instruction `data` is hex-encoded).

    ```typescript expandable
    import {
      AddressLookupTableAccount,
      Connection,
      PublicKey,
      TransactionInstruction,
      TransactionMessage,
      VersionedTransaction,
    } from "@solana/web3.js";

    const connection = new Connection(SOLANA_RPC_URL);
    const item = quote.steps[0].items[0];

    // 1. Rebuild the instructions returned by the quote
    const instructions = item.data.instructions.map(
      (i) =>
        new TransactionInstruction({
          programId: new PublicKey(i.programId),
          keys: i.keys.map((k) => ({
            pubkey: new PublicKey(k.pubkey),
            isSigner: k.isSigner,
            isWritable: k.isWritable,
          })),
          data: Buffer.from(i.data, "hex"),
        })
    );

    // 2. Resolve the address lookup tables
    const lookupTables = (
      await Promise.all(
        (item.data.addressLookupTableAddresses ?? []).map((address: string) =>
          connection
            .getAddressLookupTable(new PublicKey(address))
            .then((res) => res.value)
        )
      )
    ).filter((t): t is AddressLookupTableAccount => t !== null);

    // 3. Compile with the sponsor as the fee payer
    const message = new TransactionMessage({
      payerKey: new PublicKey(SPONSOR_SOLANA_ADDRESS),
      instructions,
      recentBlockhash: (await connection.getLatestBlockhash()).blockhash,
    }).compileToV0Message(lookupTables);

    const transaction = new VersionedTransaction(message);
    ```
  </Step>
  <Step title="Sign: sponsor first, then user" id="sign-sponsor-first-then-user">
    Sign with the sponsor key on your backend, then hand the partially signed transaction to the client for the user's signature.

    ```typescript
    // Backend: the sponsor signs first
    transaction.sign([sponsorKeypair]);

    // Client: the user signs the partially signed transaction
    const signed = await userWallet.signTransaction(transaction);
    ```
  </Step>
  <Step title="Submit and track" id="submit-and-track">
    Broadcast the signed transaction, then poll the quote's `check` endpoint until the request reaches a terminal status.

    ```typescript
    const signature = await connection.sendRawTransaction(signed.serialize());

    // Poll until "success" or "failure"
    const status = await fetch(
      `https://api.relay.link${item.check.endpoint}`
    ).then((r) => r.json());
    ```

    A failed fill refunds automatically on the origin chain in the origin currency; see [Refunds](/references/api/api_core_concepts/refunds) for the conditions.
  </Step>
</Steps>

### Fees

**`depositFeePayer`** covers the origin transaction only: Solana transaction fees and rent for accounts the deposit creates. It is independent from the destination side and from your [App Balance](/features/fee-sponsorship#funding-your-app-balance). To also sponsor destination gas or rent, use [`subsidizeFees` and `subsidizeRent`](/features/fee-sponsorship#sponsorship-parameters), which draw from your App Balance instead of the sponsor wallet.

Each trade is one Solana deposit transaction, so the sponsor pays one fee per trade. If you also want fills to start before the deposit confirms, see [Fast Fill](/features/fast-fill).

See [Solana Support](/references/api/api_guides/solana) for chain-specific parameters and transaction-size guidance.
